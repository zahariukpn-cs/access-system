# access-system
ESP32-based smart locker system with RFID authentication, ESP-NOW Master-Slave wireless architecture, status feedback, and local Web Admin UI.

# Smart Locker System

**Автоматизована система керування доступом до комірок зберігання.**

Проєкт розробляється студентською командою з метою створення безпечного та зручного способу зберігання студентських проєктів. Система дозволяє програмно керувати електронними замками, авторизувати користувачів.

## 🚀 Software
Написана програма для відкриття закритого замка. Допоки замок закритий, транзитор отримує сигнал замикати коло замка. Коли замок відкривається, програма кожні 1000 мілісекунд перевіряє статус замка, доки той знову не буде закритим. 


## Адмін програма
Це програма, яка дозволяє менеджити доступ до комірок, додавати нові картки, користувачів та комірки. 
Всі дані зберігаються в одному файлі lockers.db (SQLite). Це база даних без окремого сервера, яка складається з 4 таблиць. Дані залишаються у файлі після закриття програми, а при кожному запуску адмінка підключається до існуючого файлу. Нові таблиці створюються лише тоді, коли їх ще немає. Для роботи з базою використана бібліотеку SQLAlchemy.

---

| Таблиця | Структура |
| :--- | :--- |
| **students** | студент: id, ім'я, прізвище |
| **cards** | картка: UID (унікальний номер із чіпа) і студент, якому вона належить |
| **lockers** | комірка: id студента і унікальний номер комірки|
| **locker_assignments** | пари студент-комірка, хто до чого має доступ |

---

**Картка-студент**: багато до одного. Один студент може мати кілька карток (загубив і йому видали нову), але кожна картка належить рівно одному. Тому досить одного стовпця student_id у cards.
Доступ до комірок має студент, а не картка. Якщо студент змінює картку, доступи не треба переписувати: нову картку просто прив'язують до нього, і всі його комірки є. Стару картку можна видалити, і ніщо інше не зламається.
**Студент-комірка**: багато до багатьох. Один студент може мати кілька комірок, а в одну комірку можуть мати доступ кілька студентів. Таке не можна записати одним стовпцем (комірка належала б лише одній людині), тому зроблено окрему таблицю locker_assignments, де кожен рядок це одна пара студент-комірка.
UID зберігається як байти (hex при введенні), бо це справжній номер чипа картки.
**Каскадне видалення**. При видаленні студента автоматично зникають його картки та доступи, а при видаленні комірки зникають доступи до неї.
**Унікальність гарантована**: не може бути двох однакових UID чи двох комірок з одним номером.

### Запуск інтерфейсу
1. При запуску створюється lockers.db і таблиці, якщо їх немає.
2. Відкриває сесію (це "чернетка" змін) і чекає команди. Приймає команди add student, add card, add locker, assign, unassign, delete student/card/locker, list students/cards/lockers/free, snapshot, schema, help, exit.
3. Після кожної команди, що змінює дані, робить commit, тобто остаточно записує зміни у файл. Якщо сталася помилка, зміни скасовуються - rollback.
4. Перед видаленням запитує підтвердження.
5. Після кожної зміни генерує snapshot.json: картки з їхніми студентами та комірки кожного студента. Зчитувач читає цей файл і не залежить від SQL.
